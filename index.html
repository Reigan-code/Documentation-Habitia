2. ¿Qué es cada cosa? (glosario con la analogía de la cocina)

📜 UseCase — "El que dice QUÉ hacer, no CÓMO"
Es una clase con un método operator fun invoke(). Ejemplo real: GetTodayTasksUseCase → repository.getTodayTasks(). Está en Domain/usecase/. No sabe de HTTP ni de MySQL: solo llama a una interfaz. Por eso podés cambiar el backend y el use case ni se entera. Los 7: CompleteTask, GetHabits, GetThemePreference, GetTodayTasks, GetUpcomingReminder, GetWeeklyMeals, UpdateTheme.
🔌 Interface (Repository) — "El contrato"
Ejemplo: TaskRepository declara getTasks(): Flow, addTask(task), completeTask(id), updateTask, deleteTask. Vive en Domain/repository/. Es la promesa: "esto存在, sin importar cómo se guarda". Presentation y Data se ponen de acuerdo acá.
📦 Impl — "El empleado que hace el trabajo"
ApiTaskRepositoryImpl implementa la interfaz. Usa el HttpClient de ApiClient, construye la URL, pone el Bearer token y llama POST /Tasks. Está en Data/repository/. Si mañana cambiás de backend, solo se cambia este archivo.
✉️ DTO — "El sobre donde viaja la info"
TaskCreateDto(title, description, dueDate, priority) es lo que se serializa a JSON. Los de entrada terminan en Request/Create; los de salida en Response. Están en Data/remote/dto/. El backend tiene sus propios DTOs con el mismo nombre.
🔄 Mapper — "El traductor"
TaskMapper.toDomain(dto) convierte el JSON que vuelve en tu modelo Task. Está en Data/remote/mapper/. Lo mismo hacen HabitMapper, MealMapper, ReminderMapper, CalendarShoppingMapper.
🌐 ApiClient — "El mozo con el DNI"
Crea el HttpClient (Ktor) UNA sola vez, resuelve la IP del backend, guarda el API key de Gemini y define haabiChat() + haabiTools(). Está en Data/remote/api/ApiClient.kt.
🧠 ViewModel — "El clan que recuerda el estado"
Guarda el estado de la pantalla en StateFlow. La UI hace collectAsState() y se repinta sola. Ejemplo: HomeViewModel junta 4 use cases + 3 repositorios para calcular el progreso.
🔧 Koin (di) — "El que reparte herramientas antes de la obra"
startKoin { modules(appModule) } en MainActivity. single = una instancia (repos, sesión); factory = una nueva cada vez (ViewModels, use cases). NO conecta al backend: solo entrega los Impl ya hechos.
🪟 Haze — "El vidrio de la ventana"
hazeSource(hazeState) en la capa de fondo + hazeEffect() en la de contenido. El truco: son hermanas, no una dentro de otra, porque Haze 1.2.x excluye effects descendientes. backgroundColor en el HazeStyle es obligatorio (si no, crashea en API 31+).

5. Quién es quién, de inicio a fin

1. MainActivity (Android)
Enciende el teléfono: permiso de notificaciones, Koin, y muestra App().
2. App.kt
El director: resuelve la IP, restaura sesión, escucha HaabiEventBus, decide pantalla con Crossfade y coloca la isla + Haabi.
3. Screen (15 pantallas)
Lo que ves y tocás. Solo llama al ViewModel y muestra su StateFlow.
4. ViewModel (8)
Clan que recuerda el estado. Ej: HomeViewModel mezcla 4 use cases + 3 repos para el progreso.
5. UseCase (7)
Reglas simples: "trae las tareas de hoy", "marca completa", "trae el próximo recordatorio".
6. Repository interface (12)
El contrato entre Domain y Data.
7. Repository Impl (11)
El que realmente habla por HTTP con el backend.
8. DTO + Mapper
El sobre que viaja y el traductor que lo convierte en modelo de dominio.
9. ApiClient (Ktor)
El mozo: HttpClient, Bearer token, IP automática y Gemini.
10. Backend
Controller → Service → Entity → JPA → MySQL.
11. HaabiEventBus + StateFlow
El aviso y el repinte automático. Todo vuelve al usuario.

6. El ¿por qué? de todos los cambios

Esto es lo que aprendimos a lo largo de los 41 cortes. Cada cambio tiene una razón:

Cambio¿Por qué?
Wiring manual → Koin (di)El profesor pidió Modules + SettingProvider. Koin reparte dependencias; NO conecta al backend (eso lo hace Ktor).
NavigationBar → Row propio (isla)Material3 imponía 80dp y no se podía achicar. Ahora altura controlada desde UiConfig.
Haze: 2 cajas hermanasHaze 1.2.x excluye effects descendientes del source por zIndex. Como hermanas, el blur sí funciona.
HazeStyle con backgroundColorEs obligatorio en la ruta RenderEffect; sin él crashea en API 31+.
BASE_URL auto-detectadaAntes un flag USE_DEVICE obligaba a recompilar al cambiar de Wi-Fi. Ahora prueba 4 IPs.
JWT 15 min → 24 hEl usuario se desconectaba cada 15 minutos. Ahora la sesión dura un día.
SessionManager + DataStoreAntes se perdía el login al cerrar la app. Ahora se restaura.
HaabiAssistant eliminadoNunca pasaba actions a Gemini → no ejecutaba nada. Se quedó solo el camino nativo con function calling.
Modelo gemini-3.1 → 2.5-flashFunction calling más confiable; el prompt se recortó a ~80 tokens para bajar latencia.
HaabiActionsImpl = único puenteSi la IA quiere crear algo, debe pasar por los repos reales. Así se guarda en MySQL sí o sí.
HaabiEventBusSin él, la UI no se enteraba de lo que Haabi creaba. Ahora refresca, cambia pestaña y notifica.
InterpreteDeIngredientes tolerante"Pollo" sin cantidad daba 400 → 403. Ahora asume 1 unidad.
Categorías y catálogo a MySQLEstaban en memoria y se perdían. Ahora son tablas con seed.
Backend hexagonalEstaba en carpetas planas. Ahora cada módulo tiene domain/application/infrastructure; más orden y menos conflictos.
web/ → Controller/Lo pidió el profesor en su plantilla; se renombró sin romper nada.
Comentarios cortos estilo "sino pues…"Para que el código se lea como lo pediste: breve, claro, hablado.
DoD + 12 Queries Azure DevOpsPara que el equipo sepa cuándo algo está realmente Done y cómo auditarlo.
Gradle: JAVA_HOME 21 + sin toolchainAndroid Studio intentaba descargar Azul Zulu y el sync se colgaba. Ahora es estable.
ZIP con staging de rutas cortasEl error 0x80010135 venía de rutas >260 chars con .dex. Ahora ruta máx 130.

¿Dónde se cambia un color, según el alcance?

1. Cambiar UN botón puntual
En el Screen: buscás la línea y cambiás color = MaterialTheme.colorScheme.error por el que quieras (ej. primary). Solo afecta ese sitio.
2. Cambiar TODOS los botones primarios de la app
Andá a Core/theme/Color.kt → Primary en el ColorScheme. Todos los colorScheme.primary cambian a la vez.
3. Cambiar el vidrio (tintes del glass)
Core/theme/Glass.kt → glassTokens(). Ahí están containerAlpha, tintColor, strokeColor, specularAlpha. El HazeStyle lo consume automáticamente.
4. Cambiar la paleta que eligió el usuario
Presentation/UserMenu/CustomPaletteCreator.kt (valores HEX por defecto) o AppearanceScreen.kt → viewModel.onApplyGeneratedPalette(...) → UpdateThemeUseCase → DataStore.

Cómo encontrar cualquier cosa en CUALQUIER pantalla (método universal)

PASO 1 → Buscá el texto que ves en pantalla. Ejemplo: "Cerrar Sesión" cmd: Get-ChildItem '...\Presentation' -Recurse -Filter '*.kt' | Select-String -Pattern 'Cerrar Sesión' PASO 2 → El resultado te da ARCHIVO + LÍNEA. Ahí está el composable. PASO 3 → Mirá arriba: ¿quién lo llama? Ese es su padre (ej. HomeScreen → DayHeroCard). PASO 4 → Mirá el parámetro: ¿viene de un ViewModel? viewModel.completeTask() / viewModel.toggleHabit() / viewModel.onApplyGeneratedPalette() PASO 5 → Si es dato: ViewModel → UseCase → Interface (Domain) → Impl (Data) → DTO → Ktor → Backend. PASO 6 → Si es color/tamaño: Core/theme o Core/config → reacción automática. PASO 7 → Cambiás, compilás, probás, documentás en CAMBIOS.md.
